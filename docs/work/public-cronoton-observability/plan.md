  1. `setPublicObservable(id, { observable: true }, { db })` on a row with no prior token generates a NEW non-empty token and sets `public_observable = 1` (read back via a raw `SELECT` after the call).
  2. Calling `setPublicObservable(id, { observable: false }, { db })` then `setPublicObservable(id, { observable: true }, { db })` again returns the SAME `public_token` as step 1 (no silent rotation).
  3. Calling `setPublicObservable(id, { observable: true, regenerate: true }, { db })` returns a DIFFERENT token than the one already stored.
  4. `setPublicObservable("no-such-id", { observable: true }, { db })` throws `CodexCronotonValidationError` with message `"not found"` (reusing the existing error class from `./errors.js` — no new error type).
  5. `getCodexCronotonByPublicToken("unknown-token", { db })` returns `null`.
  6. `getCodexCronotonByPublicToken(token, { db })` returns `null` when `token` belongs to a row whose `public_observable` is currently `0` (toggle it off via `setPublicObservable(id, { observable: false })` first, then look it up by its still-stored token).
  7. `getCodexCronotonByPublicToken(token, { db })` returns the full row when the token belongs to an observable row.
  8. `getCronotonFireCounts(id, { db })` against a fixture of inserted `codex_cronoton_fires` rows (insert via raw SQL: e.g. 5 success, then 2 failure, in known `fired_at` order) reports `fired: 7, succeeded: 5, failed: 2`, `lastSuccessAt` equal to the 5th (oldest-of-the-two-failures-preceding) success's `fired_at`, `lastFailureAt` equal to the most recent failure's `fired_at`, and `currentFailStreak: 2` (only the two trailing failures, not the five successes before them).
  9. A fixture with a success sandwiched in the middle of surrounding failures (failure, failure, success, failure — in `fired_at` ascending order, so the MOST RECENT fire is the last failure) reports `currentFailStreak: 1` — proves the streak count stops at the first non-failure scanning backward from the most recent fire, not a raw failure tally over the whole history.
  10. `deriveCronotonHealth({ currentFailStreak: 0, isOverdue: false })` → `"healthy"`; `{ currentFailStreak: 1, isOverdue: false }` → `"degraded"`; `{ currentFailStreak: 2, isOverdue: false }` → `"degraded"`; `{ currentFailStreak: 0, isOverdue: true }` → `"degraded"`; `{ currentFailStreak: 3, isOverdue: false }` → `"down"`; `{ currentFailStreak: 10, isOverdue: true }` → `"down"`.
  11. `toPublicCronotonView(row, counts, firesPage, now)`'s JSON-stringified output contains NONE of the substrings `"pact_code"`, `"payload_json"`, `"signers_json"`, `"gas_payer_json"`, `"server_resolver"`, `"created_by"`, `"config_json"`, `"chain_response_json"`, `"errorMessage"` — built by stuffing a `CodexCronotonRow` fixture whose `pact_code`/`payload_json`/`signers_json`/`gas_payer_json`/`server_resolver`/`created_by`/`config_json` fields are each set to the recognizable sentinel string `"SECRET_<FIELDNAME>"`, and a `firesPage.fires` fixture containing an entry with `errorMessage: "SECRET_ERROR_TEXT"` and `chainResponse: { leak: "SECRET_CHAIN_RESPONSE" }`, then asserting `JSON.stringify(view).includes("SECRET_")` is `false`. Also assert the view has no `id` key at the top level (the internal UUID never appears).
  12. `toPublicCronotonView` sets `schedule.humanText` from `summariseSchedule` (imported from `../../schedule.js`) and omits `schedule.cron` for a `daily-at-utc` row, but includes `schedule.cron` equal to the stored expression string for a `cron-expression` row.
  13. `toPublicCronotonView` sets `triggerOnly: true` when the row's `external_fireable` is `1` (reusing `rowExternalFireable` from `./mappers.js`), and `triggerOnly: false` for an ordinary scheduled row.
  14. `toPublicCronotonView` sets `isOverdue: true` only when `row.status === "active"`, `row.next_fire_at` is non-null, and `row.next_fire_at` is before the passed-in `now`; `isOverdue: false` for a `paused` row with an equally-past `next_fire_at` (overdue only makes sense for a row the scheduler is actually supposed to be ticking).
  15. `toPublicCronotonView`'s `fires.page` entries carry `firedAt`/`status`/`chainId`/`requestKey`/`txKeys`/`recoveredAt`/`mode` and `fires.total`/`fires.limit`/`fires.offset` equal exactly to `firesPage.total`/`firesPage.limit`/`firesPage.offset` (pass-through, not recomputed).
