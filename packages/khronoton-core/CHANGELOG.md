# Changelog

All notable changes to `@ancientpantheon/khronoton-core`.

The engine's pre-extraction history lives in the AncientHoldings hub, whose inline scheduler ("Cronoton") this package extracts and generalises.

## 0.13.0 — 2026-11-20

**MINOR — chained multi-step cronoton runs: a cronoton can now express a sequential "drain→wrap→inject→evict"-shaped multi-action workflow as one unit, with a non-blocking driver, five registered built-in planners, and new per-run/per-step observability and standalone-fire routes.**

A cronoton has always been one scheduled Pact transaction. A workflow that genuinely needs several transactions in sequence — some of which fan out into N legs decided only at fire time (how many reward lanes need paying, how many stale member scores need repair) — had no way to express itself as a single schedulable unit. This release adds that as a new, fully additive capability alongside the existing one-shot cronoton; nothing about a plain cronoton's behavior changes.

- **Non-blocking submit, the keystone.** The scheduler's tick awaits a fire's confirmation inline inside a single `running`-boolean-guarded pass — fine for one transaction, impossible for a chained run (four evict legs awaited serially would freeze the *entire* scheduler, every cronoton, for up to twenty minutes). A new `"submit"` executor mode builds/signs/preflights/submits and returns immediately, never calling `listenWithTimeout`; a new optional `ChainClient.pollRequestKeys(keys, chainId)` seam polls many request keys per chain in one call (one request per chain per tick, not one per leg). `runFire`'s internals were extracted into a shared `submitTransaction` helper with zero change to `fire`'s own external behavior.
- **Schema: three new tables.** `codex_cronoton_steps` (a cronoton's static step definitions — `mode: 'single' | 'planner'`), `codex_cronoton_runs` (one run's lifecycle: `status`, `step_index`/`step_count`, `deadline_at`, `attempt`), and `codex_cronoton_run_legs` (one step's individual transactions: `status: 'pending' | 'submitted' | 'confirmed' | 'failed'`, plus a `claimed_at` lease column — see the concurrency fix below). A partial unique index self-blocks a second concurrent run per cronoton at the DB layer (`RunAlreadyInFlightError`, not a raw constraint leak); a leg row is written `pending` before it is ever submitted, mirroring the existing claim-before-fire discipline one level down.
- **Pure decision core.** `pure/run-advance.ts`'s `advanceRun(run, legs, now, policy)` is a stateless function deciding, from a run's and its legs' current state alone, one of six actions (`submit-leg`, `poll`, `advance-step`, `replan-step`, `fail-run`, `wait`) — barrier-met-before-deadline ordering, serial-vs-parallel fan handling, and the "3 of 4 legs confirm, one fails" re-plan-only-once-fully-resolved rule are all independently unit-tested branches, plus a cross-cutting invariant test proving a run can never advance past an unconfirmed leg.
- **The driver.** `runs-driver.ts`'s `driveRunOnce`/`advanceInFlightRunsOnce` execute `advanceRun`'s actions against the store and chain, wired into `startKhronotonLoop` as a third pass alongside the existing tick and manual-batch passes. A newly-due chained cronoton gets its run created and step 0 submitted within the same tick pass that created it, not merely at the next loop interval; the schedule's own `next_fire_at` keeps advancing independently of a long-lived run's self-block, by design — two independent clocks, not one gated by the other.
- **The `StepPlanner` registry + five built-in planners.** `registerStepPlanner`/`getStepPlanner` (a plain module-level map, mirroring the existing server-resolver registry) let a `mode: 'planner'` step fan out into N legs decided fresh at fire time, ported faithfully from OuronetUI's real transaction-construction logic: `ouronet.aqp-evict` (reads an on-chain evict plan, tries one `CC_FullEvictRewards` leg, fans out to one `CC_EvictSingleReward` leg per beneficiary only on a genuine gas-ceiling refusal), `ouronet.aqp-inject` (tries `CC_InjectFinalize` then `CC_Inject`, and — unlike the human-facing UI it's ported from — never refuses, propagating a genuine error instead since there's no human to hand a refusal to), `ouronet.aqp-unstall` (fans stale-member-score repair into `CCp_FvtFixSlice` batches via a newly-ported generic gas-probe-and-pack algorithm, `pure/split-plan.ts`), and `ouronet.stoa-wrap`/`ouronet.stoa-unwrap` (built as capability-construction built-ins, not fan-out built-ins — getting a Pact signer capability's scope right by hand is the dangerous part, independent of leg count; `stoa-wrap` reads the patron's live balance rather than trusting any inter-step-carried value). Every planner builds Pact code with zero interpolated values in the executed code itself — every dynamic value flows through transaction payload and a `read-string`/`read-integer`/`read-msg` placeholder; only a signer's capability line (which Pact's own signing mechanism has no env-data equivalent for) is the one documented, shape-guarded exception.
- **A run can now genuinely re-plan after a failure**, not just on its first entry — a prerequisite fix (generation-scoped legs, using the previously-unwritten `codex_cronoton_run_legs.attempt` column as a generation marker plus a new `bumpRunAttempt` store write) was needed because every planner driven before this fix would otherwise permanently defeat the barrier check the instant any single leg ever failed once — a step could never advance again, for any future attempt. This retroactively corrected a latent gap in the already-shipped `ouronet.aqp-evict` re-plan path too, not just the newly-added planners.
- **New per-run/per-step observability and standalone-fire routes.** `executeNow` now recognizes a chained row (≥1 `codex_cronoton_steps` row), starts a real run, and reports HTTP 409 (not a crash) when one is already in flight — an explicit on-demand request deserves to know it didn't happen, unlike the scheduler's own silent tick-skip. `adaptMultiTxSummary` now reads an optional per-batch `ok` field (recognizing real booleans and common stringified/numeric truthy forms, never a naive `Boolean()` coercion) to report genuine multi-tx failure instead of hardcoding success — strictly additive, falling back to today's behavior when no batch supplies the field. A new standalone `POST /cronotons/:id/steps/:index/{simulate,fire}` lets an operator preview or fire one step of a chained cronoton by index, in isolation from the run/leg lifecycle (deliberately never writing a run/leg row), behind the same confirm gate `executeNow` uses. New `GET /[id]/runs` (paginated) and `GET /[id]/runs/[runId]/legs` (404 if the run belongs to a different cronoton) make a run's full lifecycle and every leg's fire history visible through this package's own surface for the first time.
- **A genuine concurrency race was found and fixed in already-shipped Phase 3 code.** Before this release's final phase, `driveRunOnce` was only ever invoked from inside the scheduler loop's single-process re-entrancy guard; wiring `executeNow` to call it directly from an HTTP handler made a previously-deferred, previously-documented gap real: the background loop's sweep could pick up the same newly-created run and both callers could submit the same leg before either write landed. Fixed with a genuine claim-before-submit step — a new nullable `claimed_at` column plus `claimLegForSubmit`/`releaseLegClaim` (a conditional `UPDATE ... WHERE status='pending' AND claimed_at IS NULL`, mirroring the existing due-row claim idiom one level down) — proven by a dedicated end-to-end test driving two concurrent `driveRunOnce` calls on the same run and asserting the chain submit happens exactly once.
- **A follow-up cross-phase review, run after all six phases shipped, found and fixed one more CRITICAL and several more real bugs.** A planner throw on a run's very first pass (every real planner's first action is a live chain read, so a bad `planner_params_json`, a genuine Pact failure, or a transient chain outage all trigger this) left the run stuck non-terminal forever: `deadline_at` is never stamped before that point, so the deadline-based recovery path could never engage, and no code path ever marked the run terminal — permanently occupying that cronoton's one-run-at-a-time slot with no recovery short of direct DB surgery. Fixed by terminalizing the run on an unrecoverable first-entry throw, while carefully preserving the existing `maxReplanAttempts` retry budget for a transient failure during a genuine later re-plan (a first attempt at this fix was itself too broad — see below). The same round also found `runLegsHandler` leaking real transfer amounts, account identifiers, and Pact capability lines through the read-tier `GET /[id]/runs/[runId]/legs` route (now redacted, mirroring `toPublicCronotonView`'s field-by-field convention) and an uncached live `getBlockGasLimit()` fetch repeated on every leg submit and planner probe within one driver pass (now cached per chain with a short TTL) — both HIGH. A dedicated terminal re-review of the CRITICAL fix then caught a real regression in it: the new terminalize-on-throw catch was broader than intended, turning a benign concurrent-insert race into a permanent run failure and silently discarding the replan retry budget on any transient re-plan error — both fixed by narrowing the catch to only the genuinely-unrecoverable first-entry case.

Reviewed via nectar across all seven phases (base/Phase 0+1, Phase 2, Phase 3, Phase 4, Phase 4.1, Phase 4b, Phase 5) plus one additional cross-phase round after all six shipped — **33 review rounds total, 73 CONFIRMED findings fixed (or resolved via documentation where that was the proportionate response), 4 REFUTED on adversarial validation, 2 downgraded to STYLISTIC.** Standout findings: two **CRITICAL** findings (a missing Pact module-namespace prefix; a Pact-code-injection vulnerability via unescaped, unvalidated chain-read fields spliced directly into signed Pact source) were caught in round 1 of the `ouronet.aqp-evict` planner's own review, before ever shipping; a **HIGH** finding in Phase 5 caught `fireStep` firing real Pact code against a paused or terminal cronoton, bypassing the guard every other fire-capable route already enforces; a second **HIGH** in that phase is the `driveRunOnce` concurrency race described above. The follow-up cross-phase round then found a third **CRITICAL** (the stuck-run bug above) plus a **HIGH** transaction-detail leak through `runLegsHandler` — and, reviewing its own CRITICAL fix a second time, a fourth **CRITICAL** regression in that very fix (the overly-broad catch). One further real bug (floating-point noise leaking into a signed capability line and payload for realistic token balances) was caught only by behavioral verification against the real built artifact using a real measured value — no lens or unit test (all of which used clean round numbers) found it. Full history in `docs/work/khronoton-chained-runs/review.md`, its six phase-numbered siblings (`-phase-2`, `-phase-3`, `-phase-4`, `-phase-4.1`, `-phase-4b`, `-phase-5`), and `docs/work/khronoton-chained-runs-cross-phase-review/review.md`.

## 0.12.0 — 2026-11-11

**MINOR — an opt-in public observability surface: any codex-cronoton can now expose a sanitized, token-gated, unauthenticated read-only view of its schedule, health, and fire history.**

Today a cronoton's state is only visible through the authenticated admin surface (`listHandler`/`getHandler`/`firesHandler` behind `withRead` + the host's own `AuthSeam`). Nothing lets a host expose one cronoton's state to an unauthenticated, cross-origin caller — the concrete driver is embedding a mint's next-fire time and recent executions in a public-facing page — but the capability is general: every cronoton can opt in, not just one.

- **Schema.** Two new `codex_cronotons` columns: `public_token TEXT` (unique, nullable) and `public_observable INTEGER NOT NULL DEFAULT 0` (off by default). This is the first time `installSchema` has needed to add a column to an **already-provisioned** database, not just a fresh install — SQLite has no `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, so `installSchema` gains a small reusable `ensureColumn(db, table, column, columnDefSql)` helper (`PRAGMA table_info` → conditional `ALTER TABLE ADD COLUMN`) called once per column, plus a `CREATE UNIQUE INDEX IF NOT EXISTS` on `public_token` (SQLite's unique index already permits multiple `NULL`s, so non-observable rows never collide). Both a fresh install and an existing host's DB go through the identical call.
- **New `server/store/public.ts` surface.** `setPublicObservable(id, { observable, regenerate? }, dep)` toggles the flag and mints a token lazily — once, the first time a row is made observable; stable across an observable → non-observable → observable toggle (no silent rotation), with an explicit `regenerate: true` the only way to mint a new one. `getCodexCronotonByPublicToken(token, dep)` resolves a row by token, returning `null` for both an unknown token and a known-but-non-observable one — the two cases are never distinguishable, by design. `getCronotonFireCounts(id, dep)` reports whole-history aggregates (`fired`/`succeeded`/`failed`, `lastSuccessAt`/`lastFailureAt`, and a `currentFailStreak` counting only the consecutive failures immediately preceding the most recent fire). `deriveCronotonHealth({ currentFailStreak, isOverdue })` is a pure `"healthy" | "degraded" | "down"` traffic-light rule. `toPublicCronotonView(row, counts, firesPage, now?)` is the sanitizing projector — it builds the public DTO field-by-field and never spreads the row or a fire, so `pact_code`, `payload_json`, `signers_json`, `gas_payer_json`, `server_resolver`, `created_by`, `config_json`, a fire's raw `errorMessage`/`chainResponse`, and the internal row `id` can never leak through it; the public token is the only public identifier.
- **New `handlers/public.ts` → `publicCronotonHandler`.** A framework-agnostic `GET /<token>` handler, added to the barrel, that is **unauthenticated by design**: it never calls the host's `ctx.auth`/`AuthSeam` at all — a different trust tier than the admin read/confirm gates, gated purely on token validity plus the `public_observable` flag. Returns 404 for an unknown or non-observable token (identical shape, never distinguishable), 200 with the sanitized view otherwise. Paginates over the cronoton's **complete** fire history (not a fixed "last 20") via `limit`/`offset`, clamped with the same 1..100/default-50 bounds the admin `firesHandler` already uses.

New public surface is entirely additive; no existing export, column default, or response shape changes for a non-opted-in cronoton.

Reviewed via nectar across 4 rounds (correctness/conventions/security/tests lenses each round, adversarial validation throughout, 16 CONFIRMED findings total, zero REFUTED, zero STYLISTIC): round 1 (7 findings) caught the two most significant — a `triggerOnly` gap that missed a plain-`eventDriven` cronoton (no persisted column distinguishes it; fixed by gating on `next_fire_at === null` excluding terminal one-time rows) and a clamp-default mismatch (the handler's own doc comment and CHANGELOG claimed parity with the admin `firesHandler`'s default of 50 while actually defaulting to 20) — plus an `ORDER BY` tiebreak gap, a `modified_at` omission, and two test-coverage gaps; round 2 re-verified round 1's fixes and caught that the `triggerOnly` fix's own comment asserted a false invariant (`claimDueCodexCronoton` also nulls `next_fire_at` on an ordinary row, not just the terminal-intent writer), plus two more test gaps; round 3 found the round-1 `ORDER BY` tiebreak itself was wrong — it sorted on the fire row's random `crypto.randomUUID()` id instead of a chronological key, fixed to SQLite's implicit `rowid` — plus two more test-coverage gaps; round 4 added a `mapStoreError` safety net this one unauthenticated handler had been missing (every sibling handler gets it for free from `withRead`/`withConfirm`) and closed the last two test gaps (`health`'s wiring inside the projector, and the fail-streak's 1000-row cap); round 5 found that round 4's own safety net had a real (if narrow) hole — a malformed `chain_response_json` row's `JSON.parse` failure was uncaught in `server/store/fires.ts`'s shared `listFires` (unlike its sibling `parseTxKeys`, which already tolerated bad input), and Node 20+'s V8 embeds a snippet of the actual malformed input text in that error's message — which `mapStoreError`'s generic passthrough would then have forwarded verbatim into the public route's 500 body, bypassing `toPublicCronotonView`'s sanitization entirely. Fixed at the root (`fires.ts` gains the same try/catch-degrade-to-null guard as `parseTxKeys`, benefiting every current and future caller of `listFires`, not just this one route) rather than only patched at this one call site. Full history in `docs/work/public-cronoton-observability/review.md`.

**1027 specs pass.**

## 0.11.0 — 2026-09-17

**MINOR — a discoverable edit-mode Save affordance, and auto self-calibrating gas as the default for every new cronoton.**

Two independent handoffs, built and shipped together. **(1) Editor Save.** Editing an existing cronoton had no discoverable Save — the only save action was the "Commit Codex Cronoton" button on the last (Execute) tab, silently disabled under AUTO gas until a Simulate ran, with no explanation visible from any other tab. Adds an always-visible edit-mode **`SaveBar`** — Simulate, Save changes, and a live status line — rendered above the Pact editor/tabs on every tab, gated on the edited row having actually loaded (`editReady`) so it can never fire a Simulate against a blank default state during the load window. The Execute tab's own Commit button is now edit-aware ("Save changes" / "Saving…"); create mode is unaffected. A new shared `useCommitGate(state, sim)` hook (called once in `Builder.tsx`, threaded as props) keeps `SaveBar` and `ExecuteTab` reading the identical commit body and gate — no risk of two independent `builderToCommit`/`canCommit` call sites drifting apart, and no duplicate computation on every keystroke. `SaveBar`'s Save AND Simulate buttons are both `canMutate(access)`-gated in their click handlers, not just their `disabled` attribute.

**(2) Auto self-calibrating gas.** Khronoton transactions defaulted to a fixed, manually-set gas limit, so fires over-reserved gas wildly (a real pool-payout fire measured 594 gas used against a 600,000 limit). `makeEmptyBuilderState()` now defaults `autoGasLimit` to `true`. `ChainClient` gains two new optional methods: `preflightRead` (the SDK's `local` with `{preflight:true, signatureVerification:false}` — accurate gas including the transaction-size charge that plain `dirtyRead` omits) and `getBlockGasLimit` (a live `/config` fetch, best-effort with the existing static fallback). AUTO-gas fires now calibrate from `preflightRead` instead of `dirtyRead`; a runtime missing it hard-throws on an AUTO-gas fire (mirroring the 0.9.0 `gasMeta` precedent) while a MANUAL-gas fire on the same runtime is completely unaffected. A new refuse-unmineable check returns a structured failure — never a silent cap or submit — when measured gas exceeds the resolved ceiling, for both AUTO and MANUAL fires. The ceiling itself is validated (`Number.isFinite && > 0`) before use, so a buggy adapter returning `NaN`/`0`/negative can never silently defeat the refuse check.

Reviewed via nectar (2 rounds, 5 lenses then a targeted 2-lens re-pass, adversarial validation throughout): 9 CONFIRMED findings fixed — two initially-HIGH findings (SaveBar's pre-load readiness gap; its unguarded Simulate click) were validated down to MEDIUM once the actual blast radius was traced (Save itself stayed correctly disabled; the server has its own independent auth gate); the rest were MEDIUM/LOW test-coverage, duplication, and stale-doc gaps. Zero REFUTED, zero STYLISTIC. Full history in `docs/work/khronoton-editor-save-and-auto-gas/review.md`.

## 0.10.0 — 2026-09-08

**MINOR — the Builder's absolute "Gas Price (ANU)" field is gone; a cronoton now always pays the live network floor plus an optional priority buffer.**

0.9.0 made the executor floor a *stored* absolute price against the live Yin Engine floor, so a fire could no longer underprice — but the Builder UI still framed gas price as something an operator *sets*, which is the wrong model for a recurring transaction: any absolute number typed today is guaranteed to go stale as the live floor keeps rising. This finishes the redesign: the UI shows a read-only, live-refreshing "Live Network Floor" display plus an editable "Priority Buffer (ANU above floor)" (default 0), and every fire prices as `liveFloor(creationTime) + buffer`, derived fresh at build time.

- **`CodexTxConfig.gasPriceBufferAnu`** (optional, additive) — ANU to pay above the live floor; absent (every pre-migration row) defaults to 0, so existing cronotons self-heal with no DB migration. `gasPrice` is kept, `@deprecated`, read-only, for parsing historical `config_json`.
- **`ChainRuntime.gasMeta(floorAnu, bufferAnu?)`** — the buffer is a new optional 2nd parameter, non-breaking. The adapter (`blockchain/stoachain.ts`) sums `floorAnu + bufferAnu` **in ANU**, inside the adapter, before the **one** `anuToStoaNumber` conversion — summing two independently-converted STOA floats instead produces a different serialized value in roughly 1 in 5 floor/buffer pairs, reintroducing exactly the precision bug 0.9.0 fixed. `buildTransaction` always calls `gasMeta(0, config.gasPriceBufferAnu ?? 0)` now — there is no more stored absolute value to raise to a floor.
- **A negative or non-finite buffer can never underprice a fire — enforced at three independent layers**, not just the UI: `ui/builder-state.ts`'s `validateConfig` blocks commit client-side; `server/store/cronoton.ts`'s `commitCodexCronoton`/`editCodexCronoton` reject a present-and-invalid `gasPriceBufferAnu` before any write (so a caller reaching the store directly, bypassing the Builder UI, can't persist a row that silently underprices every future fire); and `blockchain/stoachain.ts`'s `gasMeta` clamps a bad buffer to 0 as a third line of defense for any `CodexTxDefinition` built outside the store entirely.
- **New `useLiveGasFloor()` hook** (`ui/builder/live-gas-floor.ts`) polls the live floor every 30s plus a `visibilitychange`/`focus` refresh (browsers throttle `setInterval` in backgrounded tabs, and this screen is routinely left open for hours) — called once in `Builder.tsx`, threaded to `ConfigTab` and `ExecuteTab`.
- **Precision fix applied a second place**: `ui/tx-size.ts`'s size estimator now computes the same floor+buffer-summed-in-ANU-then-converted-once formula the executor uses, instead of the deprecated absolute `gasPrice`.
- **Not purely additive at the UI-type layer**: `BuilderConfig.gasPriceAnu` and `CommitGateOptions.minGasPriceAnu` are **removed**, not deprecated-in-place — both lose all meaning once there is no absolute price to floor-check, and keeping them would be actively misleading. `CodexTxConfig` itself stays additive.

Reviewed via nectar (3 rounds, 5 lenses each, adversarial validation): round 1 found and fixed a HIGH gap (a negative buffer could underprice below the live floor — server-side validation was entirely absent) plus 5 lower-severity gaps in the fix's own test coverage and a minor UI re-render inefficiency; round 2 re-verified round 1's fixes and found 3 more small issues (a misleading UI label for a transient invalid state, duplicated validation logic, a test-loop robustness nit) plus 2 STYLISTIC items the validator concluded were actually already-consistent with each file's own convention; round 3 caught one last barrel-export asymmetry. All CONFIRMED findings fixed; full history in `docs/work/gas-price-buffer/review.md`.

**938 specs pass**, plus 5 real-runtime integration specs against the installed `@stoachain/*@4.4.0`. Behavioral verification against the real compiled package + a real SQLite DB confirms: a pre-migration row self-heals to buffer 0; a negative buffer is rejected at commit AND edit time with the row genuinely left unwritten/unchanged, not just "throws".

## 0.9.0 — 2026-09-07

**MINOR — scheduled transactions are priced against the chain's LIVE gas floor at fire time, not a static value stored at creation time.**

A cronoton's `gasPrice` was a plain ANU number persisted once at creation time and read back verbatim on every tick — never re-derived. Post-fork, chainweb validates a signed transaction's price against the **rising** Yin Engine floor as of that transaction's own `creationTime`, so a long-lived cronoton silently drifts below the floor and its fire is rejected. This is unattended automation: nobody is watching a 3am tick.

This was **live, not theoretical** — at the time of this release the floor stood at **11,569 ANU** while the builder's stored default was **10,000**, leaving every default-priced cronoton ~15.7% underpriced.

- **New OPTIONAL `ChainRuntime.gasMeta(floorAnu)` seam.** Returns `{ creationTime, gasPrice }` from **one** clock read. Optional so the package stays chain-POLYGLOT and `@stoachain/*` stays an optional peer dependency — a chain with no rising floor omits it. It is *not* optional in effect for a StoaChain fire: the executor **hard throws** when it is absent rather than falling back to the stored price, because a silent fallback ships the original bug to anyone who does not notice they must upgrade their runtime adapter.
- **The stored price is now a FLOOR, not a final price.** `max(stored, liveFloor(creationTime))` — an operator can still raise it above the minimum, and it can never hold a transaction below one. **Existing rows self-heal with no database migration.**
- **`creationTime` is now stamped explicitly.** `setMeta` previously omitted it, letting the Pact builder auto-stamp its own at `createTransaction()` — a second, independent clock read the price no longer corresponded to. Both fields now come from the same call, closing a tick-boundary race.
- **The AUTO-gas rebuild re-derives gas meta fresh.** The calibrated rebuild+re-sign calls the seam again rather than reusing the pre-flight build's values, so the two builds cannot straddle a tick boundary and underprice the transaction that actually gets submitted. Pinned by a regression spec that fails if the call is hoisted out of `buildTransaction`.
- **Precision.** Transaction meta now uses `anuToStoaNumber` (exact padded-decimal conversion) instead of `anuToStoa` (float division), which upstream documents as unsafe for a value chainweb hashes and validates exactly. Fixed at the meta site and at `ui/tx-size.ts`'s fee meter, whose whole job is predicting the real signed transaction's size.
- **`validateConfig` accepts an optional live floor.** `CommitGateOptions.minGasPriceAnu` replaces a hardcoded `>= 10000` gate that happily accepted an already-underpriced price; the message names the floor actually applied. Omitting it validates against the genesis floor as before — it under-rejects rather than over-rejects, and the executor raises the price at fire time regardless.
- **`blockchain/stoachain.ts` is the only place that knows the Yin Engine exists**, wrapping `@stoachain/stoa-core/gas` rather than reimplementing the arithmetic — a formula already independently reimplemented four times across the ecosystem.

**Dependencies — a coordinated family bump, not a standalone repin.** `@stoachain/stoa-core@4.4.0` peer-pins `@stoachain/kadena-stoic-legacy@4.4.0` exactly, and only `@ouronet/ouronet-core@4.6.0` accepts stoa-core 4.4.0; the three must move together or `npm install` fails to resolve. Peer + dev ranges: stoa-core `^4.3.6 → ^4.4.0`, kadena-stoic-legacy `^4.3.6 → ^4.4.0`, ouronet-core `^4.3.6 → ^4.6.0`.

New public surface — `StoaGasMeta`, the optional `ChainRuntime.gasMeta`, and `CommitGateOptions.minGasPriceAnu` — is entirely additive. A consumer injecting its own `ChainRuntime` for a StoaChain fire must add `gasMeta` (the bundled `createStoachainRuntime` supplies it); a consumer wrapping the adapter by spread picks it up with no change.

**907 specs pass, plus 5 real-runtime integration specs against the installed `@stoachain/*@4.4.0`.**

## 0.8.0 — 2026-08-03

**MINOR — the last two evented-server-resolver UI fixes: DETAIL "Schedule" reads "Evented", and a system cronoton is deletable behind a confirm-gated warning.**

Finalizes the Pythia automatic-link work. 0.7.0 made the store server-authoritative for evented resolvers; two UI gaps remained (verified live against Pythia v2.7.22–2.7.25).

- **Fix 1 — the cronoton DETAIL card's "Schedule" now reads "Evented" for a trigger-only/evented row.** It previously rendered the stored `schedule_config` ("Daily at 12:00 UTC") for a row that never fires on a clock — while Next Fire already showed "—" and the edit form already disabled the scheduler. In the bundled Builder, the Delete button is now **enabled** for an admin on a system cronoton (still admin-only) and, on click, shows a warning naming the resolver — *"This is the automaton's `<name>` template. Deleting it stops that capability until it's recreated. Delete anyway?"* — before the existing password confirm. The audit trail is preserved and a forced system delete records `forced: true`.

Behavior for ordinary scheduled cronotons is unchanged; a non-system delete and a `delete(id)`/`remove.run()` without force are byte-identical to 0.7.0, and a system delete without force still 409s. New public surface: `ConfirmOpts.force`, the widened `DeleteAction` run arg (`DeleteRunOpts`), the `deleteSystemConfirm` export, and the shared `isTriggerOnly`/`row-derive` module — all additive.

## 0.7.0 — 2026-08-03

**MINOR — server-authoritative evented resolvers: scheduleless + external-fireable enforced in the store, `GET /resolvers`, one-resolver-one-cronoton.**

0.6.0 shipped event-driven resolvers behind a **client-side** `eventDriven` flag — the guarantee lived in each consumer's proxy, not the package. 0.7.0 makes the **resolver registry** the source of truth and enforces the scheduleless contract in the **store**, so it holds for every consumer regardless of what the client sends.

- **`evented` on the resolver registry.** `SingleTxResolver` and `MultiTxResolver` gain an optional `evented?: boolean`. `createCodexCronoton`/`editCodexCronoton` derive it via `getServerResolver(name)?.evented` (a safe, acyclic store→resolvers import) and force the persisted row **scheduleless** (`next_fire_at = NULL`, excluded from `fetchDueCodexCronotons`) **and `external_fireable = 1`** — even when the caller sends a real schedule. An evented→non-evented edit correctly re-arms `next_fire_at` from the stored schedule and clears `external_fireable`; a genuine (non-evented) external-fireable row is never clobbered.
- **`GET /resolvers`.** New `listServerResolvers()` + `resolversHandler` return `{ ok: true, resolvers: [{ name, kind, evented }] }` listing every registered resolver with its flag. Exposed as a new **OPTIONAL** `resolvers()` method on the `KhronotonAdapter` read tier (implemented by both reference adapters) — deliberately **not** added to `REQUIRED_METHODS`, so pre-0.7.0 adapters still pass `assertAdapter` and the Builder degrades gracefully (falls back to the 0.6.0 `serverResolverOptions.eventDriven`) via the new `useServerResolvers` hook.
- **Builder is server-authoritative.** `eventDrivenResolver` is now `registry.evented(name) || serverResolverOptions.eventDriven` — a resolver the server marks evented hides the schedule editor, shows the event-driven notice, and commits `externalFireable: true` (derived at commit time, so switching to a non-evented resolver never leaves the flag stuck on).
- **List shows "Evented".** `CronotonList`'s next-fire cell reads **"Evented"** for a trigger-only row (`external_fireable === 1` or runtime-arg keys) instead of a blank/timestamp.
- **One resolver, one cronoton.** `createCodexCronoton` rejects a second commit reusing an already-bound `server_resolver` with `CodexCronotonValidationError` naming the existing cronoton id (→ HTTP 400).

**Note — deliberate HMAC-exposure reversal.** An evented resolver now forces `external_fireable = 1`, which makes the row HMAC-fireable. This reverses 0.6.0's "don't reuse `externalFireable`" stance and is a conscious choice: it **codifies Pythia's already-shipped production behavior** (v2.7.19/2.7.20 already force this) rather than introducing new exposure, and gives one persisted signal that the store, Builder, and list all read consistently. Manually HMAC-firing an evented resolver just re-runs its idempotent resolve, which no-ops when nothing is ready.

The published 0.6.0 `eventDriven` surface (`ServerResolverOption.eventDriven`, `CommitEnvelope.eventDriven`, the store input/patch fields, `builderToCommit` opts) is kept intact as an additive fallback; no breaking removals. Ordinary scheduled resolvers are unchanged.

**871 specs pass.**

## 0.6.1 — 2026-08-02

**PATCH — fix a CronotonList crash (white-screen) on any non-empty list.**

Opening the Khronoton admin list with ≥1 cronoton threw `TypeError: Cannot read properties of undefined (reading 'replace')` and white-screened the page — hitting every consumer the moment they had a cronoton.

- **Root cause:** `listCodexCronotons` returned a hand-picked **camelCase 9-field projection**, but the read handler declares the response as `CodexCronotonRow[]` and `CronotonList` renders full **snake_case** row fields. Only `id`/`name`/`status` (identical in both casings) actually worked; `schedule_mode`, `schedule_config_json`, `next_fire_at`, `last_fire_at`, `runtime_arg_keys`, `description`, and `server_resolver` were all silently `undefined`, and `pact_code` additionally **crashed** the unguarded `pactPreview(row.pact_code).replace(...)`. Latent since 0.3.0; surfaced once consumers had cronotons and opened the list.
- **Fix:** `listCodexCronotons` now returns full snake_case rows via `SELECT *` (mirroring `getCodexCronoton`), matching the handler's declared type and exactly what the UI reads — so the whole list renders correctly (pact preview, schedule line, last-fire badge, trigger-only detection, description, server-resolver pill), not just the crash. Plus a defensive guard so `pactPreview` treats a missing/non-string `pact_code` as `"(empty)"` and can never white-screen the page.
- `CodexCronotonListItem` is now a deprecated alias of `CodexCronotonRow` (kept so any importer still resolves). Consumers reading the list response as `CodexCronotonRow[]` (the declared type) need no change.

## 0.6.0 — 2026-08-02

**MINOR — event-driven server resolvers (scheduler-off, host-fired).**

Some server-resolver cronotons are conceptually event-driven, not time-based (they fire when an external condition becomes ready, on no meaningful clock). Previously such a resolver had to masquerade as a scheduled cronoton that polls every tick, and the Builder misleadingly showed a schedule editor for it.

- **`ServerResolverOption` gains an optional `eventDriven?: boolean`.** A consumer tags a resolver option event-driven; selecting it in the Builder commits the cronoton **scheduler-off** (`next_fire_at = NULL`, so the tick loop never auto-fires it) and replaces the schedule editor with an honest "Event-driven — the host application fires this when its trigger condition is met; there is no schedule." notice, with the schedule summary reading "Event-driven (host-fired)".
- **The host fires such a cronoton via the existing `executeNow` primitive** — no new firing primitive, no change to `executeNow`. Event-driven is threaded as its own dedicated `eventDriven` flag on the commit envelope (NOT by reusing `externalFireable`, which would wrongly expose the public HMAC trigger endpoint) — an event-driven cronoton is fired in-process by the host, never over HMAC. No new DB column: `next_fire_at = NULL` already carries the scheduler-off state, and the edit/resume paths keep it NULL correctly.
- **`server_resolver` + event-driven is allowed** (the whole feature); `server_resolver` + `runtime_arg_keys` stays forbidden.
- Also fixed in the same pass: pausing then resuming an event-driven cronoton no longer resurrects a schedule (resume now recognizes a scheduler-off row by its `next_fire_at = NULL`); and the Builder's trigger-only notice no longer wrongly claims an externally-fireable-only cronoton "declares runtime arguments".

Ordinary scheduled resolver cronotons (e.g. `pyth-flush`) are unchanged — same schedule, same UI. A non-event-driven commit body is byte-identical to 0.5.0.

**848 specs pass.**

## 0.4.0 — 2026-07-13

Made khronoton **chain-polyglot**: the package now ships the chain adapters it needs to talk to each supported chain, as a `/blockchain/<chain>` subpath family — rather than a separate npm package per chain. - **Packaging.** `/blockchain/stoachain` carries dual `{ types, import, require }` conditions and is dist-smoked under both; it builds via tsup with `@stoachain/*` external, so the byte-stable `tsc` core (`.`/`/server`/`/handlers`) is untouched.

## 0.2.0 — 2026-07-12

Added the **server/automaton engine** on a new `@ancientpantheon/khronoton-core/server` subpath — the stand-alone layer a consuming Automaton (e.g. Mnemosyne) needs to run scheduled, signed, on-chain firing. The root `.` schedule engine (7-mode math + `tickOnce`) is byte-unchanged; this is purely additive.

Lifted faithfully from the AncientHoldings hub's inline `codex-cronoton` system (~4,250 lines) and generalised behind **six injection seams** — `KeyResolver` (codex signing), `ChainRuntime` (chain client + constants), `Database` (a minimal structural handle; `better-sqlite3` satisfies it), `onAudit`, `resolveFireMode`, and a 6-field `Config` — so the package pulls no `@stoachain/*` symbol, no database driver, and no framework. What ships:

- **Store + atomic claim-before-fire (exactly-once).** The load-bearing invariant: a due fire is claimed by a conditional `UPDATE` that re-asserts the due predicate and advances `next_fire_at` in the same statement, firing only on `changes === 1`. Two overlapping ticks fire a row once — the primary double-fire guard, no leader election. Proven at the store layer and again end-to-end.
- **Headless single-transaction executor.** `executeCodexTransaction(definition, mode, ctx)` behind the `ChainRuntime` + `KeyResolver` seams: fire never throws (structured failure), dirty-read pre-flight gate (no submit on a failing pre-flight), AUTO-gas calibrate (rebuild + re-sign at the calibrated limit), and 504/derived-request-key recovery. The Hub's cross-chain SPV block is intentionally dropped.
- **Server tick + loop.** `codexCronotonTickOnce` / `processDueManualBatchesOnce` take an injected `ctx`; `startKhronotonLoop(ctx) → stop()` drives them on `config.tickIntervalMs` with a single-instance re-entrancy guard (a multi-minute inline fire never launches an overlapping tick).
- **Server-resolver registry/dispatcher.** A generic `registerServerResolver` / `fireByServerResolver` mechanism (single-tx and multi-tx kinds) between the tick and the executor; no concrete host resolvers are shipped.
- **`installSchema(db)`** — one driver-free installer for the three tables (`codex_cronotons`, `codex_cronoton_fires`, `codex_cronoton_manual_batches`), consolidating the Hub's migration chain and genericised (no host FKs/CHECKs).
- **Two definition-of-done integration tests** — a double-fire once-only proof and a codex-signs-a-scheduled-tx proof, both end-to-end against a real in-memory SQLite with mock seams.

The subpath carries the same dual `{ types, import, require }` exports condition as the root (the 0.1.1 CJS lesson), so a `tsx`/CommonJS host can `require('@ancientpantheon/khronoton-core/server')`. `better-sqlite3` is an optional dependency (reference/test backend only); the package keeps zero required runtime dependencies. Proprietary / all-rights-reserved posture unchanged.
