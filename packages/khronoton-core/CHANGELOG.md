# Changelog

All notable changes to `@ancientpantheon/khronoton-core`.

The engine's pre-extraction history lives in the AncientHoldings hub, whose inline scheduler ("Cronoton") this package extracts and generalises.

## 0.19.1 — 2026-11-26

**PATCH — fixes a real crash in `ChainedBuilder`'s Raw JSON pane: a pathologically deep (but otherwise valid) payload or planner-params value could overflow the call stack during the pane's own live preview render, crashing the whole component.**

Flagged by a security-lens finding on 0.19.0's Raw JSON import work: that review's own fix already made `jsonToChainedBuilderState` genuinely never-throwing (a deep IMPORT target is rejected with a clean parse error, since the importer eagerly re-serializes each step's raw payload/plannerParams to populate their own text fields — a deep-enough value overflows THAT guarded call first). But the Raw JSON pane's own live preview (`codeText`, a `useMemo` that re-`JSON.stringify`s the whole commit body on every render) had no equivalent guard, and — critically — is reachable through a completely different path than import: typing or pasting a deeply nested value directly into the PRE-EXISTING Payload tab's raw-JSON textarea (`PayloadTab.tsx`, nothing to do with the 0.19.0 import feature) stores it as plain text with no serialize step at all, so nothing rejects it on the way in. The next render's `codeText` computation then tries to `JSON.stringify` that reconstructed deep value as part of the whole document and throws `RangeError: Maximum call stack size exceeded`, uncaught, crashing `ChainedBuilder` entirely.

Confirmed via a real reproduction (not just code reading): mounted `ChainedBuilder`, switched a step's Payload tab to raw-JSON mode, typed a ~50,000-level-deep nested array as the payload — reliably reproduced the exact `RangeError` at `ChainedBuilder.tsx`'s `codeText` computation against the unfixed code. Fixed by wrapping `codeText`'s computation in a try/catch, falling back to a clear `"Could not render the Raw JSON preview: <message>"` string instead of propagating the exception — the pane degrades gracefully; nothing else in the component is affected (committing/simulating already went through `handleCommit`/`handleSimulate`'s own existing try/catch, unaffected by this gap). Checked for the same pattern elsewhere in the package: no equivalent unguarded live-preview `JSON.stringify` exists in the sibling single-tx `Builder.tsx` — this gap was unique to `ChainedBuilder`'s Raw JSON pane.

**1571 specs pass** (1 new, the crash reproduction + fix verification). `npx tsc --noEmit` clean; `npm run build` clean.

## 0.19.0 — 2026-11-26

**MINOR (two deliverables on the `ChainedBuilder` UI's Raw JSON pane: the "paste/import" follow-on 0.17.0 deferred, plus a brand-new generated raw-cronoton-JSON schema + field reference) — the Raw JSON pane gains a paste/upload/capture affordance that loads parsed JSON straight into builder state, and the package now publishes a machine-readable JSON Schema + human field reference for the raw chained-cronoton JSON document, generated from the package's own types and `BUILTIN_DESCRIPTORS` rather than hand-written.**

### In-builder Raw JSON unlock / paste / import

The Raw JSON pane stayed read-only (no accidental typing) but gained a "Paste / import" toggle that reveals a textarea + `.json` file upload + Capture/Cancel controls. "Capture & parse" is the whole new capability: a pure, browser-safe, never-throwing `jsonToChainedBuilderState(text)` (the inverse of `chainedBuilderToCommit`, new in `chained-builder-state.ts`) parses the pasted/uploaded document and, on success, fully replaces the builder's state — every field, step, config, payload, gas payer, signer, schedule, and `singleTxFirst` variant fills in, with `selected`/`fieldsTab`/`wholeField`/`sim` all reset to fresh-mount defaults since the new state's shape may not match the prior selection at all. On a parse error the pane shows a clear message and leaves the current state completely untouched — the author can fix the pasted text and retry without losing it. Strict (hard error, wording matching `chained-validation.ts` verbatim) on load-bearing shape — invalid JSON syntax, a non-object top level, a missing/empty/non-array `steps`, an invalid per-step `mode`; lenient (default via `makeEmptyBuilderState()`/`makeEmptyStepState()`) on everything else, including dropping an individual malformed `signers[]` entry rather than failing the whole step. `toGasPayerState`/`freshSignerId` (previously private to `builder-state.ts`) are now exported and reused by the importer rather than reimplemented. No package-side codex/signature check — the Hub's own standalone "Import Raw Cronoton" path already does that at create time; this is the nicer in-builder UX for reviewing/tweaking + Simulating a pasted draft before creating.

### Generated raw-cronoton-JSON schema + field reference

Published as new `package.json` exports entries (`./schema/raw-cronoton.schema.json`, `./schema/raw-cronoton.md`, mirroring the existing `./ui.css` static-asset precedent): a machine-readable JSON Schema and a human field reference covering the top-level shape, every step/config/gasPayer/signer field with units and ranges, the `{"$yield":"name"}` placeholder form, every schedule mode's config shape, and every registered planner's name + `plannerParams` schema. Both are build artifacts only (`npm run build`'s new `scripts/generate-raw-cronoton-schema.mjs` step) — never git-committed, so there is no second copy that can ever go stale. Generated via the **TypeScript Compiler API** walking the package's own real exported types (`ChainCommitBody`/`CodexTxConfig`/`CodexGasPayer`/`CodexSigner`/`ScheduleConfig`, …) plus `BUILTIN_DESCRIPTORS`' own runtime param metadata for the planner-params slice — never a hand-maintained schema literal. Numeric ranges that previously existed only as magic numbers inside validator code (`ttl`/`gasLimit`/`gasPriceBufferAnu` on `CodexTxConfig`; `hour`/`minute`/`daysOfWeek`/`daysOfMonth`/`intervalMinutes` on the schedule configs) are now declared once via `@minimum`/`@maximum` JSDoc tags directly on the real source types, read by the generator. A dev-only `ajv` cross-check test (never a runtime dependency of the published package) proves the generated schema and the hand-written `jsonToChainedBuilderState` parser agree on every hard-error case the parser's own suite covers.

Reviewed via nectar: deliverable 1 across 4 lenses + 3 validators + 2 fix rounds (1 STYLISTIC and 1 REFUTED left alone, every CONFIRMED finding fixed). Deliverable 2 across 3 lenses (correctness/conventions/tests — security deliberately omitted as build-time-only tooling with no external/untrusted input) + 4 parallel validators + 4 parallel fix rounds, surfacing 2 HIGH + 7 MEDIUM + 3 LOW findings, all CONFIRMED (0 REFUTED): `@minimum`/`@maximum` tags on array-typed fields were landing on the array container instead of `items`, silently making range constraints on `hours`/`daysOfWeek`/`daysOfMonth` inert; a planner-param's author-written `help` text (often safety-critical, e.g. a DPTF-revert warning) was unconditionally overridden by a generic type-shape description for `decimal`/`account`/`glyph-account` fields, silently dropping it from the published docs; the markdown renderer's nested-section walker never recursed into `oneOf`/`anyOf` branches, leaving a dead "(see below)" promise for `schedule.config`'s `several-times-per-day` variant's `times` field. Also fixed: a wrong Unicode glyph-account example (Greek kappa + colon instead of the real `Ѻ.…`/`Σ.…` convention), an error message mis-prefixed with the build script's name instead of its own module's, a hand-duplicated root-file list + `buildProgram()` helper across two test files (now a shared `test-support.ts`, also collapsing 17 redundant `ts.Program` constructions into 2 via `beforeAll` — cut that pair of test files' own runtime from 5.91s to ~1.9s), and new coverage for a previously-untested drift-protection throw and the non-object-top-level cross-check case. One meta-catch during final verification: a structural markdown-table test added by one fix round had its own pipe-count arithmetic wrong (asserted 3 unescaped `|` for a 4-column row, which needs 5) — caught by re-running the suite directly rather than trusting an individual fix round's own "green" report, given several rounds concurrently editing the same test file.

**1570 specs pass** (104 test files). `npx tsc --noEmit` clean; `npm run build` clean (including the new schema-generation step, confirmed against the real built `dist/schema/raw-cronoton.schema.json`/`.md`).

## 0.18.0 — 2026-11-25

**MINOR (the `ChainedBuilder` UI layout, settled over two owner-reviewed refinement rounds in the Hub's own browser-pane preview) — a centered, width-capped, no-horizontal-scroll-ever layout with a real flex-filling Pact editor, a split Fields pane, and a new mount-height contract.**

`ChainedBuilder` (0.17.0) shipped as a scroll-snap filmstrip with a fixed-pixel Pact-editor height and an "extended"-gated Raw JSON pane. The owner's two refinement rounds replaced that shape outright: a measured, capped, centered layout with toggle-chip panes (never more shown than the width can hold — no horizontal scroll at any width), a Pact editor that flex-fills its pane instead of clipping ~55px short, and a Fields pane split into "Step config" (default) / "Whole cronoton" tabs so step editing isn't crowded by cronoton-level fields.

- **Centered, width-capped filmstrip.** The whole rail+panes block is measured via a `ResizeObserver` and capped at `bodyMaxWidth`, then centred — the void on an ultrawide now splits evenly instead of all trailing on the right.
- **No horizontal scroll, ever.** At most `fit` panes render at once (`renderedPanes = panes.filter(visible).slice(-fit)`); Pact/Fields/Raw JSON are toggle chips (show/hide), and showing one past capacity drops the oldest. Panes size to the count actually shown, not to capacity, so two visible panes each get full width rather than a third's share.
- **The Pact editor flex-fills its pane — no clip, no vertical scroll.** `PactCodeMirror.height` widened from `number` to `number | string` (`${height}px` only for the numeric case, passed through as-is otherwise); `PactCodeEditor` gained a `fill?: boolean` prop; `StepWorkspace` gained a `fillEditor?: boolean` prop threading it through. All three are optional and default to the prior fixed-pixel behavior — no change for any OTHER consumer of these components (the single-tx `Builder`'s own Pact editor is untouched).
- **Fields pane = two tabs: `Step config` (default) | `Whole cronoton`.** Schedule moved into the Whole-cronoton tab so it no longer competes with step config for vertical space; the tab flashes amber (plus a `•` dot) while the cronoton has no name yet, clearing the instant one is typed. Name and Description now share one field via a sub-toggle.
- **New `step-result-text.ts` (`formatStepResult`/`stableStringify`), with its own test file.** A pure, zero-import, deterministic one-line rendering of a chained step's dry-run outcome, built from the already-structured yield the engine captures — never parsed back out of a formatted string. Used by the dry-run panel; reusable from a server-side fire log too.
- **New mount contract: `ChainedBuilder` now renders `height: 100%` and requires a bounded parent.** The 0.17.0 shape grew with its content in normal page flow; this shape flex-fills whatever height it's given instead, so an unbounded ancestor chain (`height: auto` all the way up) collapses it to zero height. Document this at the mount site — the reference preview harness uses `#root { height: calc(100vh - 40px); overflow: hidden }`.
- `commitChain`/`simulateChain` adapter methods remain optional, unchanged from 0.17.0.

Verification beyond the owner's own DOM-measurement + screenshot review (done against a textarea stub, since the authoring session's box couldn't load real CodeMirror): the real `PactCodeMirror`/CodeMirror was mounted end-to-end in `fill` mode inside a bounded ancestor and confirmed to render without throwing, with the `height: 100%` panel genuinely present in the DOM chain (`panel → header → flex:1 body → cm-editor`) — stronger confidence than the textarea-stub review alone could give. A pre-existing commit-routing test (`ChainedBuilder.test.tsx`, added in a prior round) needed two fixes for this refactor: a `ResizeObserver` polyfill (jsdom implements neither `ResizeObserver` nor real layout, and this component now measures its own width — without a polyfill `fit` degenerates to showing only the last visible pane, never "Pact code"), and following the moved Name field into its new "Whole cronoton" tab. Also fixed an intermittent (~1-in-5) full-suite-only flake in that file, traced to its exact cause rather than papered over: `waitFor`'s own internal polling timeout and vitest's per-test timeout both defaulted to the identical 5000ms, so under full-suite parallel load (101+ files) they could race — a `Test timed out in 5000ms` failure fired even though `waitFor`'s own timeout should have "won" first. Fixed by separating the two (an explicit, longer per-test timeout via `it(..., 15000)`, comfortably above the `waitFor` calls' own widened 8000ms), not by raising numbers at random (12/12 clean full-suite runs after the real fix, versus the earlier numbers-only widening that still flaked once more under the same stress test). Separately tightened this file's own stale header doc comment, which still described the superseded scroll-snap/"extended"-gated shape.

## 0.17.0 — 2026-11-24

**MINOR (additive across three topics; nothing existing changes) — the package now ships the chained-cronoton BUILDER as a mountable screen (`ui/chained/ChainedBuilder`) with a signed whole-chain dry-run SIMULATOR, a closed-form gas-declaration model ported from OuronetUI replacing three hand-set gas constants/fractions, and two new composable built-ins (`Transmit`/`TransmitAnew`) plus the fragment layer the chained builder composes them through.**

### Chained-cronoton builder UI + whole-chain simulator

Until now the package shipped only the single-tx `Builder` screen; a host that wanted to author a CHAINED cronoton (the 0.13.0 engine feature) had to hand-build its own multi-step UI and hand-assemble the `codex_cronoton_steps` rows. This release moves that authoring surface INTO the package, reusing the single-tx builder's own tabs so there is exactly one implementation of every dial.

- **`ChainedBuilder` (new, exported from `/ui`).** The full-page multi-step builder: a step rail (left) + the selected step's workspace (right) + the cronoton-level section (name / description / schedule / trigger-only) + **Form / Code / Side-by-side** views. It implements the **"Step 0" model by label** (one step → it is "Step 0", a plain single cronoton committed via `adapter.commit`; adding a second → the steps become "Step 1…N" and a single-tx-first variant slot appears as "Step 0", committed via `adapter.commitChain`). The per-step workspace (`StepWorkspace`) REUSES the real single-tx `ConfigTab`/`PayloadTab`/`GasPayerTab`/`SignaturesTab` + the `PactCodeEditor` (so the Ouronet-style Pact highlighting + `--khr-*` theming come for free) by synthesizing a `BuilderState` from each step — a step is byte-identical to a single cronoton on the wire. A `mode:'planner'` step omits Pact + Payload and offers a planner picker + params JSON. Also exported: `makeEmptyChainedBuilderState`/`makeEmptyStepState`/`chainedBuilderToCommit`/`canCommitChain`/`KNOWN_PLANNERS` + the `ChainedBuilderState`/`StepState` types.
- **`simulateChainBody` (new, exported from `/server`).** The SIMULATE sibling of `store/chain.ts`'s `commitChainedCronoton`: a signed whole-chain dry run that replays the chain against the live node without ever submitting. It is faithful to the real `runs-driver.ts` semantics rather than a parallel model — a `mode:'single'` step is signed-simulated and its result data captured as its yield (exactly like the driver's confirm-path `landed.result.data`); a `mode:'planner'` step is resolved through the SAME `resolvePlannerFor` + `normalizePlannerResult` the driver uses and the planner's own reported `yield` is threaded; yields flow forward through the SAME pure `resolveYieldRefs` + a prototype-less pool. "With signatures / true mode" (a signed `/local` via the injected `KeyResolver`) is the only mode — an unsigned `/local` is a shallower, app-local path the executor seam does not expose. The single-tx-first variant's dry-run verdict distinguishes a gas-ceiling refusal (`fits:false`, falls through to the chain at real fire time) from any other simulate failure (`fits:false, hardFailure:true` — the real engine THROWS rather than falling back in this case). Never throws itself: a per-step failure rides in that step's `error`, so one pass shows every step's verdict.
- **Confirm-gated handlers (`handlers/chain.ts`).** `commitChainedCronoton`/`simulateChain`, wrapped in the same `withConfirm` + audit-event discipline every other mutating/execution handler in the package already uses — this release closes the one gap where the chained-commit/whole-chain-simulate store functions had no handler-layer wrapper at all.
- **Two optional adapter methods (`commitChain?`/`simulateChain?`).** Added to the `KhronotonAdapter` seam, deliberately NOT in `REQUIRED_METHODS` — an adapter whose backend has no chained routes simply omits them and the chained builder degrades gracefully (its commit/simulate buttons announce the missing capability). Every existing single-tx consumer and fake adapter is unaffected.
- **Wire + store contract (`handlers/chain.ts`, `server/store/chain.ts`).** `ChainCommitBody`/`ChainCommitView`/`ChainSimulateView` wire types + `commitChainedCronoton` (parent row + `insertStep`×N + enable single-tx-first). The store helper is deliberately NON-atomic — the package `Database` seam omits `transaction`, so the CONSUMER wraps the call in its own real transaction. Every step's own `config` now runs through the same `assertGasPriceBufferAnu`/`assertAutoGasGate` guards the plain single-tx commit path already enforces, closing a gap where a step could silently underprice a future fire.

Deferred, flagged in the source: per-step `serverResolver` (needs a `server_resolver` column on `codex_cronoton_steps` + engine support) and raw-code **unlock/paste-to-form** (needs a JSON→state inverse parser) — neither blocks the core.

Reviewed via nectar across 4 full rounds (correctness/conventions/security/tests lenses each round, plus a 5th targeted correctness-only pass, adversarial validation throughout): round 1 (15 findings) and round 2 (8 findings) covered the original build, closing gaps including a `$yield` placeholder validated more loosely than it was resolved (a malformed ref with sibling keys could ship as a raw literal object into a live transaction) and a missing confirm-gate on the two new handlers. Round 3 (6 findings) caught a genuine HIGH-severity, pre-existing bug independent of any prior round's fixes: reordering a selected step via the rail's move control did not move the selection with it, silently leaving the editor pane showing/editing a DIFFERENT step's content under the moved step's new label — fixed by a new pure `selectedAfterMove` helper kept in lockstep with `moveStep`'s own clamping. The same round also found the local confirm-retry callback in `ChainedBuilder.tsx` diverged from the package's own canonical, tested `runGated` helper and failed OPEN (silently retried without ever gating) when a host hadn't wired a reconfirm UI — swapped for `runGated` directly, matching every other mutate path in the package. A 4th targeted pass caught the resulting compile-time mirror-type guard (keeping the hand-duplicated `ChainSimulateView`/`ChainSingleTxSimOutcome` wire/server types in sync) was itself one-directional and would miss a realistic divergence — made bidirectional. This topic was authored outside the usual nectar design/plan lifecycle (no `docs/work/` design doc precedes it, unlike the other two topics in this release); its review history lives in this release's review record rather than a `docs/work/<topic>/review.md` file.

### Closed-form gas declaration, ported from OuronetUI

Three gas-ceiling decisions used hand-set constants/fractions that OuronetUI had already proven go stale: AUTO-gas calibration (`executor.ts`) was wired to `@stoachain/stoa-core/gas`'s old nine-band multiplier ladder; the single-tx-first gas guard (`seams.ts`'s `SINGLE_TX_GAS_GUARD = 1_600_000`) left ~400,000 gas (20% of a 2,000,000 ceiling) unused on every attempt; and the fan-out planners' batch-sizing margins (`split-plan.ts`'s flat `PLANNING_MARGIN`/`CONFIRMED_MARGIN` fractions) had the same flat-fraction-of-the-whole-ceiling problem. This release ports OuronetUI's measured, closed-form model (`declareGasLimit`, built from 30 real mined transactions) directly into a new pure module and rewires all three consumers to it.

- **`pure/gas-declaration.ts` (new, internal).** `declareGasLimit`/`maxSimulatedGasAtLimit`/`maxSimulatedGasFor`/`estimateSizeChargeGas`, byte-identical in formula to OuronetUI's own, with a documented `EVIDENCE_FLOOR` below which the model defers unchanged to the legacy ladder (so very-cheap transactions keep their existing behavior exactly).
- **`executor.ts`'s AUTO-gas path** now calibrates via `declareGasLimit` instead of the old ladder for both the real fire/submit declaration AND the `simulate` preview (previously the two could disagree — the preview showed a different number than what a subsequent fire would actually declare). `simulate`'s AUTO-gas branch was also found to be signing a transaction it never needed to (only `preflightRead`s the unsigned build) — fixed to never sign at all in that branch, saving a redundant resolver/sign round-trip on every AUTO-gas preview.
- **`resolvers.ts`'s single-tx guard** now defaults to `maxSimulatedGasAtLimit(ceiling)` instead of the hand-set `1,600,000`, recovering the ~400,000 gas of headroom described above; an explicit `config.singleTxGasGuard` override still takes priority.
- **`split-plan.ts`'s batch sizing** now derives its headroom from the same model; the old flat `PLANNING_MARGIN`/`CONFIRMED_MARGIN` fractions are fully removed.

Reviewed via nectar across 5 rounds (correctness/conventions/security/tests lenses each round, adversarial validation throughout): 4 CONFIRMED findings fixed across the fix rounds, 0 REFUTED. Standout findings: `declareGasLimit`'s sub-floor path never reported a ceiling clamp even when the legacy ladder's output genuinely was clamped, contradicting the `clampedToCeiling` field's own documented contract; `executor.ts`'s `calibrateAutoGas` construction was duplicated verbatim between `runSimulate` and `submitTransaction` instead of a shared helper — exactly the drift risk that caused the original preview/declaration mismatch; and the `runSimulate` unconditional-sign gap described above. Behavioral verification drove the real compiled `dist/` artifact, confirming the new formula disagrees with the legacy ladder at `EVIDENCE_FLOOR` (21,150 vs. 27,000) and that `maxSimulatedGasAtLimit(2,000,000) = 1,999,350` (was the hand-set 1,600,000). Full history in `docs/work/ouronet-gas-declaration-port/`.

### `Transmit`/`TransmitAnew` built-ins + the composable fragment layer

The chained builder UI needed a real per-field param form for a chosen built-in (not a raw JSON blob), a read-only preview of what it will execute, and a way to COMPOSE `stoa-wrap`/`stoa-unwrap` into a larger hand-written Pact block for a single-tx step — today every registered planner owns its whole transaction and can't be spliced into anything else.

- **`builtins/descriptors.ts` (new, exported from `/ui`).** `BUILTIN_DESCRIPTORS` describing all 5 existing registered planners (`ouronet.aqp-evict`/`aqp-inject`/`aqp-unstall`/`stoa-wrap`/`stoa-unwrap`) as real per-field param forms with a `preview()` of the real entrypoints in their real try-order, plus 2 new composable-only built-ins added specifically for this: **`ouronet.stoa-transmit`/`ouronet.urstoa-transmit`** — `coin.TRANSMIT`/`coin.UR|TRANSMIT` with a `transmit`/`transmit-anew` variant (the latter for when the target account doesn't exist yet, requiring a `receiverPublicKey` to build the receiver-guard keyset). The composable built-ins' `toFragment()` produces a Pact expression + required capability lines with zero interpolated values spliced unvalidated into signed Pact source — every account/amount/namespace field is shape-validated (matching the real planners' own `ACCOUNT_SHAPE` idiom) before it can reach a capability line or the executed expression.
- Zero imports from `server/executor.js`/`@stoachain/*`/`node:crypto` — this module is pure, browser-safe data, re-exported from the existing `/ui` barrel rather than a new `package.json` exports-map entry.

Reviewed via nectar across 2 rounds (correctness/conventions/security/tests lenses each round, adversarial validation throughout): 4 CONFIRMED findings fixed (1 MEDIUM correctness, 3 MEDIUM security), 1 REFUTED, 1 STYLISTIC left open. The security findings were the most significant: `patronAccount`/`targetAccount`/`sender`/`receiver` account fields, `amountCeiling`/`capAmount` decimal fields, and the `namespace` field were all being spliced into capability lines or the executed `pactExpr` with no validation — a value containing a quote or paren could restructure the signed capability a signer actually grants. Fixed by validating every one of these fields against a shape regex (mirroring the real planners' own `ACCOUNT_SHAPE` guard) before any splice, with a dedicated regression test per field across all 4 composable descriptors proving the exact attacker-controlled-quote/paren payloads now throw before any fragment is built. Behavioral verification drove the real compiled `dist/ui/index.js` → `dist/builtins/descriptors.js` artifact through all 4 of design.md's core scenarios. Full history in `docs/work/builtin-descriptors/`.

Verified together across all three topics: `npx tsc --noEmit` clean, `npx vitest run` clean, `npm run build` clean (`tsc -p tsconfig.build.json && tsup && node scripts/bundle-css.mjs`).

## 0.16.0 — 2026-11-23

**MINOR (fixes a bug that made every real `ouronet.aqp-inject` reward injection revert, plus a small required-field addition) — `injectPlanner` now sources `executor` from `planner_params_json` instead of deriving it from the step's signer, and distinguishes a too-stale-to-inject failure from a genuine error.**

`injectPlanner` (`server/planners/inject.ts`) derived the Pact `executor` argument it sends to `CC_InjectFinalize`/`CC_Inject` from the step's own first signer's public key (`` `k:${signers[0].publicKey}` ``). Verified directly against the deployed Ouronet contracts (`05_FVT.pact`/`04_RPS.pact`): the reward debit this `executor` names bottoms out in `XI_FvtInjectCore`'s `(ref-TFT::C_Transfer patron injector AQP|SC_NAME reward-dptf-id amount true)`, a DPTF (True-Fungible) transfer whose balances are keyed by `(token-id, Ouronet glyph account)`. A `k:` native account has no DPTF balance row for any token, so every real inject this planner has ever driven reverted — it has never actually been able to move a reward. `patron` carries only the IGNIS fee and is validated for existence only; it holds nothing.

- **`InjectPlannerParams` gains a required `executor: string`** (a glyph Ouronet account, e.g. `Ѻ.…`/`Σ.…`) — a **breaking addition** to the planner's `planner_params_json` contract: any existing step configuration must add this field (its reward injections were silently reverting anyway, so there is no working prior configuration this could regress). Validated non-empty and rejected if `k:`-prefixed (the exact bug class being fixed) — shape-only, matching every sibling planner's "trust the contract beyond shape" posture; there is no established glyph-account-format validator anywhere in this codebase to reuse. `signers[0]` is still required (a step with zero signers can never build or sign a leg at all) but is no longer the source of the `executor` value — it still proves ownership/guard of that glyph account at sign time.
- **A new distinguishable `InjectRequiresUnstallError`** (exported from `server/planners/inject.js`, public via the existing `export * from "./planners/inject.js"` barrel) is thrown when `CC_InjectFinalize` fails (stale present users remain) AND the heavier `CC_Inject` fallback is *also* refused specifically for exceeding the gas ceiling — a numeric `gasUsed` on an `{ok:false}` simulate result, the same refuse-unmineable signal `evictPlanner` already reads. Any OTHER second-failure reason still throws a plain `Error`, unchanged. This deliberately does **not** fan out within the same step the way `evictPlanner` does: `CC_Inject`'s cost is driven by an inline stale-user-fix loop running *inside one atomic Pact transaction* (confirmed directly against `05_FVT.pact`'s `CC_Inject` body) — there is no on-chain entrypoint splitting `CC_Inject` itself into independent legs the way `URHC_BuildEvictPlans` hands evict a ready-made array of independent per-beneficiary legs, and this package's chained-run engine submits every leg of one `mode:'planner'` step in parallel with no serial-then-parallel mixing within a single step — a same-step fan-out would race `CC_InjectFinalize` against the fix-slices and revert against stale state that hasn't landed yet. Instead, `InjectRequiresUnstallError` is a signal: the caller reacts by inserting an `ouronet.aqp-unstall` step before this one in the chain (the mechanism already built for exactly this, via `CCp_FvtFixSlice`/`splitPlan`), rather than this planner inventing new cross-cutting engine machinery.

## 0.14.0 — 2026-11-20

**MINOR — step-to-step yield carry: a chained run's steps can now hand a specific computed value forward to a later step, closing the one real gap 0.13.0's chained-runs feature shipped with.**

New nullable `codex_cronoton_steps.yield_as` column, applying uniformly to both step modes: the step row itself always owns the yield's name, never the planner.
- **Producing a yield.** A `mode:'planner'` step's `StepPlanner` can now optionally return `{ legs, yield }` instead of a bare leg array (the old bare-array return stays valid forever — none of the 5 existing built-ins were forced to change). - **Consuming a yield.** A `{"$yield": "<name>"}` placeholder is resolved recursively against the run's pool right before a step executes — for planner-mode steps this means **zero code changes to any planner, built-in or custom**: `ouronet.aqp-inject` still just parses `planner_params_json` normally and sees an already-resolved decimal string. An unresolvable reference throws a named `YieldNotFoundError` (now a public export) rather than silently resolving to `null`.

## 0.13.0 — 2026-11-20

**MINOR — chained multi-step cronoton runs: a cronoton can now express a sequential "drain→wrap→inject→evict"-shaped multi-action workflow as one unit, with a non-blocking driver, five registered built-in planners, and new per-run/per-step observability and standalone-fire routes.**

A cronoton has always been one scheduled Pact transaction. A workflow that genuinely needs several transactions in sequence — some of which fan out into N legs decided only at fire time (how many reward lanes need paying, how many stale member scores need repair) — had no way to express itself as a single schedulable unit. This release adds that as a new, fully additive capability alongside the existing one-shot cronoton; nothing about a plain cronoton's behavior changes.

- **Non-blocking submit, the keystone.** The scheduler's tick awaits a fire's confirmation inline inside a single `running`-boolean-guarded pass — fine for one transaction, impossible for a chained run (four evict legs awaited serially would freeze the *entire* scheduler, every cronoton, for up to twenty minutes). A new `"submit"` executor mode builds/signs/preflights/submits and returns immediately, never calling `listenWithTimeout`; a new optional `ChainClient.pollRequestKeys(keys, chainId)` seam polls many request keys per chain in one call (one request per chain per tick, not one per leg). `runFire`'s internals were extracted into a shared `submitTransaction` helper with zero change to `fire`'s own external behavior.
- **Schema: three new tables.** `codex_cronoton_steps` (a cronoton's static step definitions — `mode: 'single' | 'planner'`), `codex_cronoton_runs` (one run's lifecycle: `status`, `step_index`/`step_count`, `deadline_at`, `attempt`), and `codex_cronoton_run_legs` (one step's individual transactions: `status: 'pending' | 'submitted' | 'confirmed' | 'failed'`, plus a `claimed_at` lease column — see the concurrency fix below). A partial unique index self-blocks a second concurrent run per cronoton at the DB layer (`RunAlreadyInFlightError`, not a raw constraint leak); a leg row is written `pending` before it is ever submitted, mirroring the existing claim-before-fire discipline one level down.
- **Pure decision core.** `pure/run-advance.ts`'s `advanceRun(run, legs, now, policy)` is a stateless function deciding, from a run's and its legs' current state alone, one of six actions (`submit-leg`, `poll`, `advance-step`, `replan-step`, `fail-run`, `wait`) — barrier-met-before-deadline ordering, serial-vs-parallel fan handling, and the "3 of 4 legs confirm, one fails" re-plan-only-once-fully-resolved rule are all independently unit-tested branches, plus a cross-cutting invariant test proving a run can never advance past an unconfirmed leg.
- **The driver.** `runs-driver.ts`'s `driveRunOnce`/`advanceInFlightRunsOnce` execute `advanceRun`'s actions against the store and chain, wired into `startKhronotonLoop` as a third pass alongside the existing tick and manual-batch passes. A newly-due chained cronoton gets its run created and step 0 submitted within the same tick pass that created it, not merely at the next loop interval; the schedule's own `next_fire_at` keeps advancing independently of a long-lived run's self-block, by design — two independent clocks, not one gated by the other.
- **The `StepPlanner` registry + five built-in planners.** `registerStepPlanner`/`getStepPlanner` (a plain module-level map, mirroring the existing server-resolver registry) let a `mode: 'planner'` step fan out into N legs decided fresh at fire time, ported faithfully from OuronetUI's real transaction-construction logic: `ouronet.aqp-evict` (reads an on-chain evict plan, tries one `CC_FullEvictRewards` leg, fans out to one `CC_EvictSingleReward` leg per beneficiary only on a genuine gas-ceiling refusal), `ouronet.aqp-inject` (tries `CC_InjectFinalize` then `CC_Inject`, and — unlike the human-facing UI it's ported from — never refuses, propagating a genuine error instead since there's no human to hand a refusal to), `ouronet.aqp-unstall` (fans stale-member-score repair into `CCp_FvtFixSlice` batches via a newly-ported generic gas-probe-and-pack algorithm, `pure/split-plan.ts`), and `ouronet.stoa-wrap`/`ouronet.stoa-unwrap` (built as capability-construction built-ins, not fan-out built-ins — getting a Pact signer capability's scope right by hand is the dangerous part, independent of leg count; `stoa-wrap` reads the patron's live balance rather than trusting any inter-step-carried value). Every planner builds Pact code with zero interpolated values in the executed code itself — every dynamic value flows through transaction payload and a `read-string`/`read-integer`/`read-msg` placeholder; only a signer's capability line (which Pact's own signing mechanism has no env-data equivalent for) is the one documented, shape-guarded exception.
- **A run can now genuinely re-plan after a failure**, not just on its first entry — a prerequisite fix (generation-scoped legs, using the previously-unwritten `codex_cronoton_run_legs.attempt` column as a generation marker plus a new `bumpRunAttempt` store write) was needed because every planner driven before this fix would otherwise permanently defeat the barrier check the instant any single leg ever failed once — a step could never advance again, for any future attempt. This retroactively corrected a latent gap in the already-shipped `ouronet.aqp-evict` re-plan path too, not just the newly-added planners.
- **New per-run/per-step observability and standalone-fire routes.** `executeNow` now recognizes a chained row (≥1 `codex_cronoton_steps` row), starts a real run, and reports HTTP 409 (not a crash) when one is already in flight — an explicit on-demand request deserves to know it didn't happen, unlike the scheduler's own silent tick-skip. `adaptMultiTxSummary` now reads an optional per-batch `ok` field (recognizing real booleans and common stringified/numeric truthy forms, never a naive `Boolean()` coercion) to report genuine multi-tx failure instead of hardcoding success — strictly additive, falling back to today's behavior when no batch supplies the field. A new standalone `POST /cronotons/:id/steps/:index/{simulate,fire}` lets an operator preview or fire one step of a chained cronoton by index, in isolation from the run/leg lifecycle (deliberately never writing a run/leg row), behind the same confirm gate `executeNow` uses. New `GET /[id]/runs` (paginated) and `GET /[id]/runs/[runId]/legs` (404 if the run belongs to a different cronoton) make a run's full lifecycle and every leg's fire history visible through this package's own surface for the first time.

WHERE status='pending' AND claimed_at IS NULL`, mirroring the existing due-row claim idiom one level down) — proven by a dedicated end-to-end test driving two concurrent `driveRunOnce` calls on the same run and asserting the chain submit happens exactly once.

## 0.9.0 — 2026-09-07

**MINOR — scheduled transactions are priced against the chain's LIVE gas floor at fire time, not a static value stored at creation time.**

A cronoton's `gasPrice` was a plain ANU number persisted once at creation time and read back verbatim on every tick — never re-derived. Post-fork, chainweb validates a signed transaction's price against the **rising** Yin Engine floor as of that transaction's own `creationTime`, so a long-lived cronoton silently drifts below the floor and its fire is rejected. This is unattended automation: nobody is watching a 3am tick.

This was **live, not theoretical** — at the time of this release the floor stood at **11,569 ANU** while the builder's stored default was **10,000**, leaving every default-priced cronoton ~15.7% underpriced.

- **New OPTIONAL `ChainRuntime.gasMeta(floorAnu)` seam.** Returns `{ creationTime, gasPrice }` from **one** clock read. Optional so the package stays chain-POLYGLOT and `@stoachain/*` stays an optional peer dependency — a chain with no rising floor omits it. It is *not* optional in effect for a StoaChain fire: the executor **hard throws** when it is absent rather than falling back to the stored price, because a silent fallback ships the original bug to anyone who does not notice they must upgrade their runtime adapter.
- **The stored price is now a FLOOR, not a final price.** `max(stored, liveFloor(creationTime))` — an operator can still raise it above the minimum, and it can never hold a transaction below one. **Existing rows self-heal with no database migration.**
- **`creationTime` is now stamped explicitly.** `setMeta` previously omitted it, letting the Pact builder auto-stamp its own at `createTransaction()` — a second, independent clock read the price no longer corresponded to. Both fields now come from the same call, closing a tick-boundary race.
- **The AUTO-gas rebuild re-derives gas meta fresh.** The calibrated rebuild+re-sign calls the seam again rather than reusing the pre-flight build's values, so the two builds cannot straddle a tick boundary and underprice the transaction that actually gets submitted. Pinned by a regression spec that fails if the call is hoisted out of `buildTransaction`.
- **Precision.** Transaction meta now uses `anuToStoaNumber` (exact padded-decimal conversion) instead of `anuToStoa` (float division), which upstream documents as unsafe for a value chainweb hashes and validates exactly. Fixed at the meta site and at `ui/tx-size.ts`'s fee meter, whose whole job is predicting the real signed transaction's size.
- **`validateConfig` accepts an optional live floor.** `CommitGateOptions.minGasPriceAnu` replaces a hardcoded `>= 10000` gate that happily accepted an already-underpriced price; the message names the floor actually applied. Omitting it validates against the genesis floor as before — it under-rejects rather than over-rejects, and the executor raises the price at fire time regardless.
- **`blockchain/stoachain.ts` is the only place that knows the Yin Engine exists**, wrapping `@stoachain/stoa-core/gas` rather than reimplementing the arithmetic — a formula already independently reimplemented four times across the ecosystem.

**Dependencies — a coordinated family bump, not a standalone repin.** `@stoachain/stoa-core@4.4.0` peer-pins `@stoachain/kadena-stoic-legacy@4.4.0` exactly, and only `@ouronet/ouronet-core@4.6.0` accepts stoa-core 4.4.0; the three must move together or `npm install` fails to resolve. Peer + dev ranges: stoa-core `^4.3.6 → ^4.4.0`, kadena-stoic-legacy `^4.3.6 → ^4.4.0`, ouronet-core `^4.3.6 → ^4.6.0`.

New public surface — `StoaGasMeta`, the optional `ChainRuntime.gasMeta`, and `CommitGateOptions.minGasPriceAnu` — is entirely additive. A consumer injecting its own `ChainRuntime` for a StoaChain fire must add `gasMeta` (the bundled `createStoachainRuntime` supplies it); a consumer wrapping the adapter by spread picks it up with no change.

Added the **server/automaton engine** on a new `@ancientpantheon/khronoton-core/server` subpath — the stand-alone layer a consuming Automaton (e.g. Mnemosyne) needs to run scheduled, signed, on-chain firing. The root `.` schedule engine (7-mode math + `tickOnce`) is byte-unchanged; this is purely additive.

Lifted faithfully from the AncientHoldings hub's inline `codex-cronoton` system (~4,250 lines) and generalised behind **six injection seams** — `KeyResolver` (codex signing), `ChainRuntime` (chain client + constants), `Database` (a minimal structural handle; `better-sqlite3` satisfies it), `onAudit`, `resolveFireMode`, and a 6-field `Config` — so the package pulls no `@stoachain/*` symbol, no database driver, and no framework. What ships:

- **Store + atomic claim-before-fire (exactly-once).** The load-bearing invariant: a due fire is claimed by a conditional `UPDATE` that re-asserts the due predicate and advances `next_fire_at` in the same statement, firing only on `changes === 1`. Two overlapping ticks fire a row once — the primary double-fire guard, no leader election. Proven at the store layer and again end-to-end.
- **Headless single-transaction executor.** `executeCodexTransaction(definition, mode, ctx)` behind the `ChainRuntime` + `KeyResolver` seams: fire never throws (structured failure), dirty-read pre-flight gate (no submit on a failing pre-flight), AUTO-gas calibrate (rebuild + re-sign at the calibrated limit), and 504/derived-request-key recovery. The Hub's cross-chain SPV block is intentionally dropped.
- **Server tick + loop.** `codexCronotonTickOnce` / `processDueManualBatchesOnce` take an injected `ctx`; `startKhronotonLoop(ctx) → stop()` drives them on `config.tickIntervalMs` with a single-instance re-entrancy guard (a multi-minute inline fire never launches an overlapping tick).
- **Server-resolver registry/dispatcher.** A generic `registerServerResolver` / `fireByServerResolver` mechanism (single-tx and multi-tx kinds) between the tick and the executor; no concrete host resolvers are shipped.
- **`installSchema(db)`** — one driver-free installer for the three tables (`codex_cronotons`, `codex_cronoton_fires`, `codex_cronoton_manual_batches`), consolidating the Hub's migration chain and genericised (no host FKs/CHECKs).
- **Two definition-of-done integration tests** — a double-fire once-only proof and a codex-signs-a-scheduled-tx proof, both end-to-end against a real in-memory SQLite with mock seams.

The subpath carries the same dual `{ types, import, require }` exports condition as the root (the 0.1.1 CJS lesson), so a `tsx`/CommonJS host can `require('@ancientpantheon/khronoton-core/server')`. `better-sqlite3` is an optional dependency (reference/test backend only); the package keeps zero required runtime dependencies. Proprietary / all-rights-reserved posture unchanged.
